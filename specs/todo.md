Standing decisions from batch 1 (Carl, November 19–20, 2026; goal: the GPU API reads as if designed from the start):

- The device module is `gpu`, compiled only with the `cubecl-cuda` feature (name and Beta wording kept despite the general `_experimental` preference), with docs.rs feature badges. CubeCL versions are pinned and CubeCL types are exposed.
- GPU reads are exactly three, each the counterpart of a CPU read of a local file: `Bed::read_cubecl`, `ReadOptionsBuilder::read_cubecl`, and `Bed::read_cubecl_with_options`, linked both ways with their CPU counterparts. `gpu::client()` and `gpu::memory_cleanup()` are functions. Device 0 only, documented with a `CUDA_VISIBLE_DEVICES` recipe.
- GPU calls return `Box<gpu::Error>` (`Bed`, `Unavailable`, `Server`, `TooLarge`, `Cuda`); `Error::Bed` wraps ordinary read errors, and `BedErrorPlus` matches 1.2 exactly. The standardizer's `InvalidVariance` is crate-private. Python GPU failures raise `RuntimeError`; wrapped read failures keep the existing exception mapping.
- CPU-only builds support Rust 1.85 (resolver fallback, locked CI tests on 1.85); GPU support needs Rust 1.95. `_cubecl-cpu-test` is internal and runs the kernels on CubeCL's CPU runtime, including under `--all-features`.
- Deferred, each addable later without breaking anything: GPU read-and-fill with a public `CubeClMatrix::empty` (if per-block allocation cost justifies it), choosing a GPU device (when a real user needs several GPUs in one process), and GPU reads from the cloud.
- Declined: uploading an `ndarray` into a `CubeClMatrix`, writing from one (use `to_cpu` then `write`), a public Rust GPU standardizer, and a `BedCloud`-like GPU type.
